PHASE 4 — FULL REPOSITORY RENDERING AUDIT

Inspect every relevant route and all shared components, not just the homepage.

A. Layout shifts and CLS

Investigate:

- Images, logos and icons without reserved dimensions.
- Fonts that change text width or page geometry after loading.
- Header and navigation height changes.
- Upload areas that expand after JavaScript initialization.
- Cards and tool grids that change height after rendering.
- Banners, notices, advertisements or asynchronous content that push existing content down.
- Buttons whose labels or dimensions change during loading.
- Missing skeleton dimensions or inconsistent placeholders.
- Responsive breakpoints that cause overflow or abrupt reflow.
- Content injected above already-rendered content.
- Loading indicators that unexpectedly alter surrounding layout.

Reserve space for asynchronous content and assets where appropriate.

Use width, height or aspect-ratio reservations for images and stable dimensions for elements where suitable.

Do not simply hide shifting content to reduce CLS. Correct the underlying cause.

B. Initial rendering and critical path

Investigate:

- Render-blocking CSS.
- Unnecessary synchronous JavaScript.
- Oversized entry bundles.
- Unnecessary hydration or initialization work.
- Excessive component nesting or repeated renders.
- Expensive calculations during initial rendering.
- Unnecessary network requests before the upload interface appears.
- Large global stylesheets.
- Unused fonts and excessive font weights.
- Duplicate requests and assets.
- Third-party resources that delay first render.

Prioritize content needed for the first visible screen.

Do not lazy-load the main heading, primary upload area, visible critical images or other essential above-the-fold content.

C. JavaScript and bundle optimization

Inspect the production build output.

Where justified and supported by the current architecture:

- Introduce route-level code splitting.
- Dynamically import heavy, tool-specific modules.
- Load PDF processing libraries only when required.
- Remove verified unused dependencies.
- Reduce duplicate dependencies and unnecessary polyfills.
- Optimize imports without changing existing tool behavior.
- Avoid loading every tool's implementation on every route.
- Reduce avoidable React re-renders.
- Move expensive noncritical work away from initial rendering when safe.

Do not split code blindly or add new dependencies just to improve an audit score.

D. CSS, fonts and assets

Inspect:

- CSS bundle size and duplicated selectors.
- Fonts, weights, formats and loading strategy.
- Image dimensions, formats and compression.
- SVG usage and icon-library overhead.
- Background images and offscreen content.
- Asset preloading and preconnect hints.
- Unnecessary animations or expensive paint effects.
- Large shadows, filters or blur effects where profiling shows a real cost.

Preserve the existing visual design, brand identity, spacing, typography and colors.

Use preload or preconnect only for resources proven to be critical.

Lazy-load below-the-fold images and noncritical media where appropriate.

E. Responsive rendering

Test practical mobile, tablet, laptop and desktop viewport sizes.

Inspect:

- Horizontal overflow.
- Overlapping cards and buttons.
- Text clipping and unexpected wrapping.
- Header and navigation alignment.
- Upload area width and height.
- Tool grids and card dimensions.
- Dialogs and menus extending outside the viewport.
- Missing content and incorrect responsive visibility.
- Touch-target sizing.
- Unexpected changes after fonts or images finish loading.

Do not solve layout problems by hiding content, removing features or using arbitrary fixed widths.

F. Loading and error states

Inspect every existing tool's shared and route-specific loading behavior.

Ensure:

- The page shell renders promptly.
- The user sees a stable upload interface.
- Loading indicators have a clear purpose.
- Error and empty states are understandable.
- Failed asset or network requests do not leave permanent loading screens.
- The interface does not jump unnecessarily between loading, ready and error states.
- Repeated clicks do not start duplicate operations.
- Existing upload validation and progress behavior remain intact.

Keep PDF file processing separate from the time required to render the initial page.

G. Firebase Hosting and delivery

Inspect the actual deployment configuration and generated build output.

Check:

- Immutable caching for fingerprinted assets.
- Appropriate HTML caching and revalidation.
- Brotli or Gzip delivery where supported.
- Compression of text assets.
- Asset paths and cache invalidation.
- Duplicate or unnecessarily large production assets.
- SPA fallback configuration.
- Direct access to nested tool routes.
- Missing assets and incorrect MIME types.

Do not change domains, hosting providers, deployment architecture or production configuration unnecessarily.

Do not expose secrets, API keys or environment variables.

PHASE 5 — IMPLEMENTATION STRATEGY

After the audit, implement only fixes supported by repository inspection, browser evidence or build analysis.

Prioritize:

P0 — Critical:

- Broken rendering, missing content, failed routes, severe layout shifts, blocking errors and unusable upload interfaces.

P1 — High impact:

- Unnecessary initial JavaScript, large render-blocking assets, delayed primary content and serious network bottlenecks.

P2 — Medium impact:

- Font and image optimization, redundant requests, avoidable re-renders and noncritical layout instability.

P3 — Low impact:

- Minor cleanup that has a demonstrable benefit without introducing unnecessary risk.

For every implemented fix:

1. Identify the affected file or component.
2. Explain the verified problem.
3. Make the smallest safe change.
4. Preserve current APIs, component contracts and route behavior.
5. Run the available tests and production build.
6. Check for regressions.
7. Measure again where tooling permits.

Avoid speculative rewrites and cosmetic refactoring unrelated to performance.
